ЗАДАНИЕ НА ВКР

     АННОТАЦИЯ
     Работа посвящена разработке веб-сайта «Khodakov Fashion House» 
— многофункциональной веб-платформы для автоматизации продаж и 
продвижения услуг по кастомизации текстильных изделий.
     В работе исследуется предметная область B2B/B2C-сегмента рынка 
услуг по нанесению принтов и вышивки на одежду, анализируются 
существующие аналоги и обосновывается необходимость разработки 
собственного решения.
     В работе дается характеристика применяемых технологий: 
фреймворк Laravel (PHP), чистый стек HTML5/CSS3, система управления 
контентом MoonShine, а также средства контейнеризации Docker и 
сборщик Vite.
     Подробно описывается архитектура приложения, инфологическая 
модель данных, реализованный механизм автоматической генерации slug-
идентификаторов для публикаций блога, SEO-оптимизация страниц, а 
также процедура тестирования программного продукта.
     Работа содержит 24 листа текста, 11 рисунков, 6 таблиц, 3 
приложения.

     ВВЕДЕНИЕ
     Современный рынок услуг по кастомизации текстильных изделий 
демонстрирует устойчивый рост: согласно отраслевым исследованиям, 
объём мирового рынка персонализированной продукции ежегодно 
увеличивается на 9–12 %. Всё большее число предпринимателей, бизнесов 
и частных лиц обращается к услугам по нанесению вышивки, DTF-печати 
и шелкографии для создания корпоративного мерча, персональных 
изделий и брендированной продукции.
     В условиях высокой конкурентной среды ключевым фактором 
успеха становится наличие профессиональной веб-платформы, способной 
не только представить компанию в интернете, но и автоматизировать 
процессы приёма и обработки заявок, формирования базы клиентов и 
управления контентом. Отсутствие такого инструмента у предприятия ИП 
Ходаков М.Г. (бренд «Khodakov Fashion House», г. Новомосковск, Тульская 
область), специализирующегося на предоставлении B2B и B2C услуг по 
нанесению машинной вышивки и цифровой печати на текстильные 
изделия, обусловило необходимость выполнения данной выпускной 
квалификационной работы. Связь работы с задачами конкретного 
предприятия заключается в создании полноценной веб-платформы, 
которая решит проблему ручной обработки заявок и обеспечит 
масштабирование бизнеса.
     Цель работы — проектирование и разработка веб-сайта «Khodakov 
Fashion House», обеспечивающего лидогенерацию, презентацию услуг и 
автоматизированный процесс обработки входящих обращений AS-IS от 
клиентов в B2B/B2C сегменте.
     Объект исследования — процессы продажи, продвижения и 
автоматизации приёма заказов на услуги по кастомизации текстильных 
изделий.
     Предмет исследования — веб-приложение на основе фреймворка 
Laravel с административной панелью и SEO-оптимизацией.
     Для достижения поставленной цели необходимо решить 
следующие задачи:
•	провести анализ предметной области и существующих веб-решений 
в сфере кастомизации одежды;
•	разработать техническое задание на создание веб-сайта;
•	спроектировать архитектуру приложения и инфологическую модель 
данных;
•	реализовать публичную часть сайта: главную страницу, каталог 
услуг, раздел «О нас», блог с SEO-оптимизацией (slug-
маршрутизация), страницу контактов и политику 
конфиденциальности;
•	разработать административную панель для управления 
публикациями блога на базе MoonShine;
•	провести функциональное и структурное тестирование 
разработанного программного продукта;
•	подготовить руководство системного программиста и руководство 
оператора;
•	разработать мероприятия по охране труда и безопасности 
жизнедеятельности для рабочего места программиста.
     Обоснование актуальности. До начала разработки компания 
«Khodakov Fashion House» не имела собственного веб-представительства: 
Процесс обработки входящих обращений AS-IS характеризовался высокой 
долей ручного труда через мессенджеры (такие как Telegram, WhatsApp, 
MAX), что значительно ограничивало охват аудитории и создавало 
административную нагрузку на менеджера и руководителя, так как на 
данный момент – это один человек. Разработанный программный продукт 
устраняет указанные недостатки, обеспечивая круглосуточный приём 
обращений, структурированное хранение данных о заявках и эффективное 
SEO-продвижение за счёт семантических URL (slug) для публикаций 
блога, что упрощает работу руководителю и менеджеру.
     Практическая значимость работы состоит в том, что 
разработанный веб-сайт передан заказчику и используется в реальной 
коммерческой деятельности предприятия.
     Пояснительная записка состоит из введения, шести разделов, 
заключения, списка использованных источников и трёх приложений.
 
     1 АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ И БИЗНЕС-
ПРОЦЕССОВ
1.1	Анализ предметной области
     Модель AS-IS (дословно «как есть») — это фиксация и описание 
реального технологического или бизнес-процесса в том виде, в каком он 
существует на предприятии в текущий момент, включая все его 
неэффективные элементы, узкие места (bottlenecks), временные задержки и 
избыточные ручные операции.
     Предметная область проекта охватывает сферу предоставления B2B 
и B2C услуг по нанесению вышивки и принтов на текстильные изделия. 
Khodakov Fashion House работает в нескольких взаимосвязанных 
направлениях:
1.	Ателье и индивидуальная машинная вышивка на одежде и текстиле 
(B2C / малый B2B) - футболки, худи, шевроны, логотипы, патчи, 
именные надписи, подарочные изделия.
2.	Брендирование и мерч для бизнеса и сообществ (B2B) - 
корпоративная одежда, мерч для брендов, мероприятий, клубов и 
команд.
3.	Онлайн-платформа (сайт-лендинг + лидогенерация) для приёма 
заявок, демонстрации кейсов, методов нанесения и формирования 
сообщества вокруг бренда.
     По своей сути - это гибрид: офлайн-ателье, небольшое производство 
и онлайн-витрина. 
     Анализ предметной области выявил следующие характеристики 
бизнес-процессов предприятия до внедрения системы:
•	процесс обработки входящих обращений AS-IS осуществлялся 
исключительно через мессенджер Telegram в ручном режиме, что 
ограничивало доступность услуг для новых клиентов и сильно 
нагружало руководство и менеджеров;
•	отсутствовал структурированный каталог услуг с описанием 
технологий и ценообразования, доступный в сети Интернет, что 
создавало путаницу у пользователей и потенциальных заказчиков;
•	компания не имела инструментов контент-маркетинга (блог, кейсы) 
для органического поискового продвижения;
•	управление информацией о заявках велось в неформализованном 
виде, что способствовало утечке важных данных, потере заказов.  
     Анализ конкурентных веб-решений в данной сфере показал, что 
лидирующие платформы (stanleystella.com, printify.com, printful.com, 
pnhd.ru, comerch.ru) используют следующие ключевые элементы: чёткую 
структуру каталога услуг, многошаговые формы заказа, блог для SEO-
продвижения и интеграцию с мессенджерами. Именно эти элементы были 
приняты за основу при проектировании системы.
     Эффективность внедрения разрабатываемой системы 
выражается в переходе от децентрализованной обработки данных к 
единому информационному контуру. Внедрение веб-ресурса призвано 
решить задачу снижения показателя Time-to-Market (времени от 
первичного интереса клиента до фиксации ТЗ в базе данных) и 
минимизировать риски потери лидов из-за человеческого фактора в 
мессенджерах.
     
     1.2 Описание бизнес-процессов
     В рамках проектирования информационной системы было 
выполнено перепроектирование и оптимизация ключевых контуров 
деятельности предприятия. На основе результатов предпроектного 
обследования построена целевая модель TO-BE («как должно быть»), 
определяющая логику функционирования бизнес-процессов после 
интеграции разработанного программного продукта в инфраструктуру 
студии  Khodakov Fashion House.
     Разработанный веб-ресурс и административная панель позволяют 
полностью автоматизировать два сквозных бизнес-процесса предметной 
области.
     1. Процесс взаимодействия с клиентом и обработки входящих 
заявок(TO-BE)
     Целью автоматизации данного процесса является перевод 
коммуникации с заказчиками в структурированное русло, минимизация 
времени обработки лидов и исключение потери данных. Алгоритм 
выполнения процесса включает следующие последовательные этапы:
1.	Инициация сессии: пользователь (потенциальный клиент) 
осуществляет переход на веб-ресурс студии.
2.	Информационное ознакомление: пользователь изучает 
представленный интерактивный каталог B2B/B2C услуг, знакомится 
с технологическими особенностями производства в блоге и 
просматривает портфолио выполненных кейсов.
3.	Навигация: пользователь переходит в целевой раздел «Контакты».
4.	Заполнение формы: пользователь вносит персональные данные и 
параметры заказа в структурированную форму обратной связи и 
отправляет запрос.
5.	Серверная валидация: на стороне бэкенда (фреймворк Laravel) 
система выполняет автоматическую проверку входящих данных на 
корректность и безопасность.
6.	Регистрация в БД: прошедшая валидацию заявка персистентно 
сохраняется в реляционной базе данных.
7.	Нотификация менеджмента: система инициирует автоматическую 
отправку уведомления администратору о поступлении нового 
обращения.
8.	Обратная связь: система генерирует и выводит на экран пользователя 
интерфейсное подтверждение об успешной отправке и регистрации 
формы.
     2. Процесс управления информационным контентом (TO-BE)
     Процесс направлен на обеспечение автономности контент-
менеджера при публикации маркетинговых материалов, новостей и 
примеров работ для поискового продвижения (SEO) без привлечения 
разработчиков. Жизненный цикл процесса состоит из следующих шагов:
1.	Аутентификация: администратор (контент-менеджер) проходит 
процедуру авторизации в изолированной панели управления 
MoonShine.
2.	Инициация публикации: в CRUD-интерфейсе ресурса «Блог» 
пользователь нажимает кнопку создания новой записи.
3.	Заполнение контента: администратор заполняет текстовые поля 
(заголовок, тело статьи) и загружает графическое изображение через 
медиа-менеджер.
4.	Автоматическая генерация идентификатора: на этапе сохранения 
записи программная логика системы автоматически преобразует 
кириллический заголовок в уникальный, SEO-оптимизированный 
латинский slug-идентификатор (формирование ЧПУ - понятных 
человеку URL).
5.	Публикация: данные транслируются в базу данных, и статья 
мгновенно становится доступной в публичной зоне веб-ресурса по 
сформированному уникальному адресу.
     Детальные графические модели автоматизированных бизнес-
процессов, отражающие функциональную структуру системы и потоки 
данных, представлены в виде диаграмм вариантов использования (Use 
Case Diagram) и диаграмм потоков данных (DFD) в Приложении Б.
     
     1.3 Ключевые риски предметной области
     Функционирование и внедрение разрабатываемой информационной 
системы сопряжено с рядом специфических рисков, характерных для 
предметной области высокотехнологичного текстильного производства и 
индивидуального брендинга. В рамках системного анализа были выделены 
и классифицированы следующие ключевые риски, а также выработаны 
технические и организационные меры по их минимизации:
1.	Непонимание клиентами технологических особенностей 
производства. Специфика машинной вышивки и конструирования 
одежды требует от заказчика базовых знаний о плотности стежков, 
ограничениях по детализации мелких элементов и типах тканей. 
Неосведомленность клиентов часто приводит к завышенным или 
технически нереализуемым ожиданиям от готового изделия.
o	Метод минимизации: Интеграция в разработанный веб-ресурс 
интерактивного портфолио с высокой детализацией 
макросъемки, создание информационного блока (FAQ) и 
разделов блога, наглядно объясняющих возможности и 
ограничения применяемых технологий.
2.	Ошибки и некорректность в исходных макетах и техническом 
задании (ТЗ). Предоставление клиентами растровых изображений 
низкого разрешения или некорректных векторных файлов приводит 
к искажению дизайна при оцифровке (создании программы для 
вышивальной машины) и, как следствие, к браку готовой продукции.
o	Метод минимизации: Реализация на стороне веб-ресурса 
четких и жестко структурированных форм обратной связи с 
валидацией вводимых данных и инструкциями по форматам 
загружаемых файлов, а также автоматизация первичного сбора 
требований, исключающая двусмысленность при 
коммуникации.
3.	Срыв сроков при производстве крупных тиражей. Высокая 
загрузка производственных мощностей, поломки оборудования или 
человеческий фактор могут привести к нарушению договорных 
обязательств перед оптовыми заказчиками, что критично для 
коммерческой деятельности предприятия.
o	Метод минимизации: Обеспечение высокой скорости 
обработки и фиксации поступающих заявок через 
разработанную систему. Автоматическое сохранение 
обращений в базе данных и мгновенное уведомление 
администратора позволяют менеджменту оперативнее 
распределять нагрузку на производство на ранних этапах 
планирования.
4.	Зависимость от внешних поставщиков текстиля и расходных 
материалов. Нестабильность поставок качественной основы под 
нанесение (худи, футболки, ткани), фурнитуры или 
специализированных нитей напрямую влияет на непрерывность 
производственного цикла студии.
o	Метод минимизации: Использование информационной 
системы для оперативного информирования клиентов об 
актуальном ассортименте. Административная панель 
MoonShine позволяет менеджеру в реальном времени 
актуализировать контент на сайте, скрывая недоступные 
позиции или оперативно предлагая альтернативные варианты 
сырья.
5.	Репутационные риски в цифровой среде. В сфере премиального 
сегмента одежды и брендинга любое негативное упоминание, 
технический сбой при обработке заказа или задержка ответа могут 
повлечь за собой отток клиентов и падение лояльности к бренду.
o	Метод минимизации: Повышение отказоустойчивости 
системы за счет серверной валидации данных, дублирования 
уведомлений для менеджеров и внедрения автоматического 
подтверждения отправки формы для клиента. Это гарантирует 
прозрачность взаимодействия на этапе первого обращения 
(процесс TO-BE).
     
     1.4 Выбор методологии разработки
     Для проектирования и реализации разрабатываемого программного 
продукта была выбрана гибкая методология разработки (Agile) на 
основе итеративного (эволюционного) подхода.
     В отличие от классической каскадной модели (Waterfall), требующей 
жесткой и неизменяемой фиксации всех требований на начальном этапе, 
итеративный подход позволяет декомпозировать сложный процесс 
разработки на последовательность коротких, управляемых циклов 
(итераций). Выбор данной методологии обусловлен высокой динамикой 
предметной области (сфера моды и интернет-маркетинга), 
необходимостью постоянного контроля качества интерфейса со стороны 
заказчика, а также постепенным наращиванием функциональной 
сложности системы.
     Процесс создания информационной системы был разделен на четыре 
ключевые итерации, каждая из которых представляла собой мини-цикл 
разработки (анализ, проектирование, кодирование, тестирование и 
демонстрация):
•	Итерация 1. Проектирование архитектуры и реализация 
публичных страниц (Ядро системы). На данном этапе был 
развернут каркас приложения на фреймворке Laravel, настроена 
конфигурация окружения и спроектирована структура базы данных 
для хранения заявок. Результатом итерации стала работоспособная 
frontend-часть сайта: главная страница, каталоги услуг, портфолио и 
страница контактов с формой обратной связи. Это позволило на 
раннем этапе согласовать с заказчиком минимально жизнеспособный 
продукт (MVP) и общую визуальную концепцию.
•	Итерация 2. Разработка динамического модуля (Блог и Slug-
генерация). В рамках второй итерации фокус сместился на 
расширение функционала публичной зоны. Была реализована логика 
вывода динамического контента, спроектирована база данных для 
публикаций и внедрен механизм автоматической генерации 
уникальных SEO-идентификаторов (slug) из заголовков статей. Это 
обеспечило формирование понятных человеку URL-адресов (ЧПУ) 
непосредственно в момент создания записи.
•	Итерация 3. Интеграция административной панели (MoonShine). 
Третий этап был посвящен автоматизации процессов управления 
контентом со стороны контент-менеджера и администратора. На базе 
пакета MoonShine было спроектировано изолированное рабочее 
пространство (админ-панель), настроена ролевая модель доступа, 
созданы CRUD-ресурсы (интерфейсы создания, чтения, обновления 
и удаления) для управления блогом, услугами и поступающими от 
клиентов заявками.
•	Итерация 4. Поисковая оптимизация (SEO), адаптивность и 
финальное тестирование. Заключительная итерация включала в 
себя работы по техническому аудиту и тонкой настройке системы. 
Была проведена кроссбраузерная и адаптивная верстка под 
различные типы мобильных и десктопных устройств, 
оптимизирована скорость загрузки страниц (настройка сборщика 
Vite), прописаны мета-теги и выполнено комплексное 
интеграционное тестирование сквозных бизнес-процессов (от 
отправки формы пользователем до отображения заявки в админ-
панели).

     Обоснование выбора Laravel. Laravel является одним из наиболее 
популярных PHP-фреймворков, реализующих паттерн MVC (Model–View–
Controller). Ключевые преимущества фреймворка применительно к 
данному проекту:
•	встроенный ORM Eloquent обеспечивает удобное взаимодействие с 
базой данных без написания «сырых» SQL-запросов;
•	система маршрутизации (файл routes/web.php) позволяет 
декларативно описывать все URL-адреса приложения;
•	встроенный класс Str::slug() из 
пакета Illuminate\Support\Str используется для автоматической 
генерации человекочитаемых URL (slug) из заголовков публикаций 
блога;
•	механизм миграций баз данных обеспечивает версионирование 
схемы БД;
•	система шаблонизатора Blade позволяет организовать 
переиспользуемые компоненты (общий макет layouts/main.blade.php).
     Обоснование выбора MoonShine. Административная панель 
MoonShine выбрана как готовое решение для быстрой реализации CRUD-
интерфейсов. Ресурс PostResource обеспечивает полный цикл управления 
публикациями: создание с прикреплением изображения, редактирование и 
удаление записей. Это позволило сосредоточить усилия разработчика на 
бизнес-логике и публичном интерфейсе, а не на написании шаблонного 
административного кода.
     Обоснование выбора Vite. Инструмент сборки Vite обеспечивает 
компиляцию и минификацию таблиц стилей CSS и JavaScript-модулей. В 
режиме разработки Vite предоставляет hot module replacement (HMR), что 
ускоряет цикл разработки. Интеграция с Laravel осуществляется через 
директиву @vite() в Blade-шаблонах.

     3.2.2 Реализация механизма генерации slug и SEO-
маршрутизации
     Одной из ключевых технических особенностей разработанного 
программного продукта является реализация системы человекочитаемых 
URL-адресов (slug) для публикаций блога, обеспечивающей SEO-
оптимизацию.
     Принцип работы. При создании новой публикации 
модель Post автоматически генерирует уникальный slug из заголовка без 
участия пользователя. Процесс генерации реализован через механизм 
событий жизненного цикла Eloquent-модели — хук creating, который 
срабатывает непосредственно перед сохранением новой записи в базу 
данных.
     Алгоритм генерации slug:
1.	Из заголовка публикации формируется базовый slug с помощью 
метода Str::slug($title, '-', 'ru'), который транслитерирует кириллицу в 
латиницу и заменяет пробелы дефисами.
2.	Выполняется проверка уникальности сформированного slug в 
таблице posts.
3.	При обнаружении коллизии (slug уже существует) к базовому 
значению добавляется числовой суффикс (-1, -2 и т.д.) с 
последующей повторной проверкой — до нахождения уникального 
значения.
4.	Найденное уникальное значение присваивается полю $post-
>slug перед сохранением.
     Маршрутизация по slug реализована через переопределение 
метода getRouteKeyName() в модели Post, возвращающего строку 'slug'. 
Это указывает Laravel использовать поле slug вместо стандартного id при 
разрешении маршрутных параметров (Route Model Binding). В результате 
публикации доступны по URL вида /post/nazvanie-stati вместо /post/1.
     SEO-преимущества. Применение slug-маршрутизации обеспечивает 
следующие преимущества с точки зрения поисковой оптимизации:
•	URL-адреса публикаций содержат ключевые слова из заголовка, что 
повышает релевантность страниц в поисковых системах;
•	семантические URL воспринимаются пользователями как более 
понятные и надёжные по сравнению с числовыми 
идентификаторами;
•	каждая публикация блога индексируется поисковыми роботами как 
самостоятельная страница с уникальным URL.
     Помимо slug-маршрутизации, в проекте реализован ряд 
дополнительных SEO-мер:
•	наличие файла site.webmanifest для корректного отображения сайта 
на мобильных устройствах;
•	подключение favicon в форматах 16×16, 32×32 и apple-touch-icon 
(180×180) для отображения в браузерах и поисковой выдаче;
•	использование атрибута lang="ru" в теге <html> для указания языка 
документа поисковым системам;
•	мета-тег viewport для корректной работы адаптивного дизайна и 
учёта принципа Mobile First в ранжировании Google;
•	использование семантических HTML5-
тегов: <nav>, <section>, <article>, <footer> для структурирования 
контента страниц;
•	атрибут alt у всех значимых изображений (например, alt="{{ $post-
>title }}" в шаблоне блога) для обеспечения доступности и SEO.
 
     4 ТЕСТИРОВАНИЕ ПРОГРАММНОГО ОБЕСПЕЧЕНИЯ
     4.1 Основные термины и их соотношение
     В соответствии с принятой терминологией в области обеспечения 
качества программного обеспечения, в рамках данного раздела 
применяются следующие понятия:
     Тестирование — процесс выполнения программы с целью 
обнаружения ошибок путём проверки соответствия реального поведения 
системы ожидаемому поведению, определённому техническим заданием.
     Верификация — процесс оценки системы или её компонентов с 
целью определения, удовлетворяют ли результаты данного этапа 
разработки условиям, сформулированным в начале этого этапа (проверка 
«правильно ли сделано изделие»).
     Валидация — процесс оценки системы в ходе или в конце 
разработки, целью которого является определение соответствия системы 
установленным требованиям (проверка «правильное ли изделие сделано»).
     Тест-кейс — набор входных данных, предусловий выполнения, 
ожидаемых результатов и постусловий, разработанный с целью проверки 
того или иного требования к системе.
     Дефект (баг) — несоответствие фактического результата 
выполнения программы ожидаемому результату, зафиксированное в тест-
кейсе.
     Применительно к разрабатываемому веб-сайту «Khodakov Fashion 
House» тестирование подразделяется на два основных 
вида: функциональное (проверка соответствия функций системы 
требованиям ТЗ) и структурное (анализ кода на предмет корректности 
архитектурных решений).
     4.2 Статистические методы устранения ошибок
     В ходе разработки веб-сайта для выявления и устранения дефектов 
применялись следующие методы:
     Инспекция кода (Code Review). Ключевые модули системы — 
модель Post, контроллер PostController, механизм генерации slug и 
ресурс PostResource — подвергались ручной инспекции с целью 
выявления логических ошибок, нарушений стандартов кодирования PSR-
12 и потенциальных уязвимостей безопасности.
     Пошаговая отладка. Встроенные средства отладки Laravel 
(файл storage/logs/laravel.log) использовались для диагностики ошибок 
времени выполнения, возникавших в процессе разработки, в частности 
при реализации логики генерации slug и сохранения медиафайлов.
     Регрессионное тестирование. После внесения каждого 
значительного изменения в кодовую базу (например, добавления 
миграции add_slug_to_posts_table) проводилась повторная проверка ранее 
работавших функций с целью исключения их деградации.

     4.4 Структурное тестирование
     Структурное тестирование проводилось методом «белого ящика» — 
с анализом исходного кода приложения. В проекте присутствует файл 
конфигурации phpunit.xml, что свидетельствует о готовности среды для 
автоматизированного тестирования.
     В ходе структурного анализа проверялись:
•	корректность маршрутизации: все маршруты в 
файле routes/web.php были верифицированы командой php artisan 
route:list — все 8 маршрутов (GET /, GET /about, GET /contact, GET 
/services, GET /privacy, GET /blog, POST /blog, GET /post/{post:slug}) 
зарегистрированы корректно;
•	логика генерации slug: алгоритм в 
методе booted() модели Post проверен на граничные случаи — 
пустой заголовок, заголовок из специальных символов, коллизия при 
совпадении slug;
•	серверная валидация: правила в 
классе StorePostRequest (required, string, max:255 для title; required, str
ing, max:5000 для text) протестированы с намеренно некорректными 
входными данными;
•	безопасность загрузки файлов: в 
методе store() контроллера PostController изображение сохраняется 
через $request->file('image')->store('posts', 'public') — используется 
диск public, файлы хранятся за пределами директории public/ и 
доступны через символическую ссылку (php artisan storage:link), что 
исключает прямое выполнение загруженных файлов.

     Шаг 9 (альтернативный). Запуск через Docker. При наличии 
установленного Docker Compose приложение запускается 
командой docker-compose up -d, которая автоматически поднимает 
контейнеры с веб-сервером, PHP и СУБД согласно конфигурации docker-
compose.yml.
     5.4 Проверка программы
     После завершения установки работоспособность приложения 
проверяется следующим образом:
•	открыть в браузере адрес http://localhost (или 
настроенный APP_URL) — должна открыться главная страница

     Вход в административную панель:
1.	Ввести в адресной строке браузера адрес /moonshine.

1.	Нажать кнопку «Создать».

1.	В списке публикаций нажать кнопку редактирования нужной записи.
2.	Внести необходимые изменения в поля формы.
3.	Нажать «Сохранить».
     Удаление публикации:
1.	В списке публикаций нажать кнопку удаления нужной записи.
2.	Подтвердить удаление в диалоговом окне.

     РАЗДЕЛ 6. ОХРАНА ТРУДА И БЕЗОПАСНОСТЬ 
ЖИЗНЕДЕЯТЕЛЬНОСТИ
     6.1 Анализ опасных и вредных производственных факторов
     При разработке и эксплуатации веб-сайта «Khodakov Fashion House» 
основным рабочим инструментом является персональный электронный 
вычислительный машина (ПЭВМ). Работа с ПЭВМ относится к категории 
умственного труда и сопряжена с воздействием ряда вредных и опасных 
производственных факторов.
     В соответствии с ГОСТ 12.0.003-2015 «Опасные и вредные 
производственные факторы. Классификация» при работе с ПЭВМ 
выявлены следующие факторы:
     Физические факторы:
•	повышенный уровень электромагнитного излучения от монитора и 
системного блока;
•	пониженная или повышенная освещённость рабочей зоны;
•	длительное статическое напряжение мышц шеи, спины и рук при 
работе в нерациональной позе;
•	монотонность выполняемой работы.
     Психофизиологические факторы:
•	зрительное напряжение при длительной работе с экраном монитора;
•	нервно-психическое напряжение при решении сложных задач 
программирования и отладки;
•	умственное перенапряжение.
     6.2 Нормативная база
     Организация рабочего места разработчика/оператора должна 
соответствовать требованиям следующих нормативных документов:
•	СанПиН 1.2.3685-21 «Гигиенические нормативы и требования к 
обеспечению безопасности и (или) безвредности для человека 
факторов среды обитания» — устанавливает требования к 
микроклимату, освещённости и уровню шума на рабочих местах с 
ПЭВМ;
•	ГОСТ 12.2.032-78 «Система стандартов безопасности труда. Рабочее 
место при выполнении работ сидя. Общие эргономические 
требования» — устанавливает требования к организации рабочего 
места;
•	Федеральный закон № 426-ФЗ от 28.12.2013 «О специальной оценке 
условий труда».
     6.3 Требования к организации рабочего места
     Требования к освещению. Рабочее место должно иметь 
естественное освещение (коэффициент естественной освещённости — не 
менее 1,2 %) и искусственное освещение. Освещённость на поверхности 
рабочего стола в зоне размещения рабочего документа должна составлять 
300–500 лк. Монитор следует располагать боком к окну, чтобы избежать 
отражения световых бликов на экране.
     Требования к микроклимату. Оптимальные параметры 
микроклимата на рабочем месте оператора ПЭВМ: температура воздуха — 
21–23 °С (холодный период) и 22–24 °С (тёплый период); относительная 
влажность воздуха — 40–60 %; скорость движения воздуха — не более 0,1 
м/с.
     Требования к рабочей позе. Монитор следует располагать на 
расстоянии 50–70 см от глаз оператора, верхний край экрана — на уровне 
глаз или несколько ниже. Кресло должно обеспечивать поддержку 
поясничного отдела позвоночника.
     6.4 Меры по снижению воздействия вредных факторов
     Для снижения негативного воздействия вредных производственных 
факторов рекомендуется:
•	соблюдать режим труда и отдыха: при работе с ПЭВМ непрерывная 
продолжительность работы не должна превышать 2 часов; 
рекомендуются перерывы продолжительностью 10–15 минут каждые 
45–60 минут работы;
•	выполнять комплексы упражнений для глаз (правило 20-20-20: 
каждые 20 минут смотреть на объект, удалённый на 20 футов, в 
течение 20 секунд) и гимнастику для мышц шеи и рук;
•	использовать монитор с антибликовым покрытием и настраивать 
яркость и контрастность экрана в соответствии с условиями 
освещённости рабочего помещения.
     6.5 Пожарная безопасность
     Помещения, в которых размещается серверное оборудование и 
рабочие места операторов ПЭВМ, должны соответствовать требованиям 
пожарной безопасности в соответствии с Федеральным законом № 123-ФЗ 
«Технический регламент о требованиях пожарной безопасности». 
Серверное помещение должно быть оборудовано автоматической системой 
пожарной сигнализации и первичными средствами пожаротушения 
(углекислотные огнетушители ОУ-2 или ОУ-5). Электрическое 
оборудование должно быть заземлено. Прокладка кабелей должна 
исключать их перегрев и механическое повреждение.

     А.2 Описание выходных данных системы
     А.2.1 Страница списка публикаций блога (GET /blog)
     Выходными данными страницы блога является отформатированный 
список публикаций, извлекаемый из базы данных запросом:
     Post::query()->latest()->get()
     Каждая карточка публикации в выходном представлении содержит:
•	автора публикации (статическое значение «KHODAKOV TEAM»);
•	дату публикации в формате дд.мм.гггг (из поля created_at);
•	заголовок публикации (title);
•	изображение (путь storage/posts/имя_файла или внешний URL);
•	анонс текста (text);
•	гиперссылку на полную публикацию по URL /post/{slug}.
     При отсутствии публикаций в базе данных выводится сообщение: 
«Постов пока нет».
     А.2.2 Страница отдельной публикации (GET /post/{slug})
     Выходными данными страницы публикации являются:
•	дата публикации в формате «дд Месяц гггг» (например, «15 апреля 
2026»);
•	заголовок публикации в теге <h1> (обеспечивает SEO-иерархию 
заголовков);
•	изображение публикации с атрибутом alt="{{ $post->title }}";
•	полный текст публикации с сохранёнными переносами строк 
(nl2br(e($post->text)));
•	ссылка «← Назад в блог».
     Заголовок вкладки браузера (<title>) динамически устанавливается 
равным $post->title, что является элементом SEO-оптимизации.

     В.2 Модель публикации с автогенерацией slug
     Файл: app/Models/Post.php
     <?php
     
     namespace App\Models;
     
     use Illuminate\Database\Eloquent\Factories\HasFactory;
     use Illuminate\Database\Eloquent\Model;
     use Illuminate\Support\Str;
     
     class Post extends Model
     {
         use HasFactory;
     
         /**
          * Поля, доступные для массового присвоения.
          *
          * @var list<string>
          */
         protected $fillable = [
             'title',
             'slug',
             'image',
             'text',
         ];
     
         /**
          * Хук жизненного цикла модели: автоматическая генерация 
уникального slug
          * из заголовка публикации при создании новой записи.
          */
         protected static function booted(): void
         {
             static::creating(function (Post $post) {
                 // Транслитерируем заголовок и формируем базовый slug
                 $base = Str::slug($post->title, '-', 'ru');
                 $slug = $base;
                 $i = 1;
     
                 // Проверка уникальности; при коллизии добавляем числовой 
суффикс
                 while (Post::where('slug', $slug)->exists()) {
                     $slug = $base . '-' . $i++;
                 }
     
                 $post->slug = $slug;
             });
         }
     
         /**
          * Переопределение ключа маршрутной привязки (Route Model 
Binding).
          * Laravel будет использовать поле 'slug' вместо 'id' при 
разрешении
          * параметра {post} в маршруте /post/{post:slug}.
          */
         public function getRouteKeyName(): string
         {
             return 'slug';
         }
     }
 
     
     В.3 Контроллер публикаций блога
     Файл: app/Http/Controllers/PostController.php
     <?php
     
     namespace App\Http\Controllers;
     
     use App\Http\Requests\StorePostRequest;
     use App\Models\Post;
     use Illuminate\Http\RedirectResponse;
     use Illuminate\View\View;
     
     class PostController extends Controller
     {
         /**
          * Отображение списка публикаций блога (в обратном 
хронологическом порядке).
          */
         public function index(): View
         {
             $posts = Post::query()
                 ->latest()
                 ->get();
     
             return view('blog', compact('posts'));
         }
     
         /**
          * Сохранение новой публикации.
          * Изображение сохраняется на диск 'public' в директорию 'posts/'.
          * Slug генерируется автоматически моделью Post через хук 
booted().
          */
         public function store(StorePostRequest $request): RedirectResponse
         {
             $postData = $request->validated();
             $postData['image'] = $request->file('image')->store('posts', 'public');
     
             Post::query()->create($postData);
     
             return redirect()
                 ->route('blog')
                 ->with('success', 'Пост успешно добавлен.');
         }
     
         /**
          * Отображение страницы отдельной публикации.
          * Параметр $post разрешается через Route Model Binding по 
полю 'slug'.
          */
         public function post(Post $post): View
         {
             return view('post', compact('post'));
         }
     }
 
     
     В.4 Ресурс административной панели MoonShine
     Файл: app/MoonShine/Resources/PostResource.php
     <?php
     
     declare(strict_types=1);
     
     namespace App\MoonShine\Resources;
     
     use Illuminate\Database\Eloquent\Model;
     use App\Models\Post;
     
     use MoonShine\Resources\ModelResource;
     use MoonShine\Decorations\Block;
     use MoonShine\Fields\ID;
     use MoonShine\Fields\Image;
     use MoonShine\Fields\Text;
     use MoonShine\Fields\Textarea;
     use MoonShine\Fields\Field;
     use MoonShine\Components\MoonShineComponent;
     
     /**
      * CRUD-ресурс для управления публикациями блога через 
административную панель.
      *
      * @extends ModelResource<Post>
      */
     class PostResource extends ModelResource
     {
         protected string $model = Post::class;
     
         protected string $title = 'Посты';
     
         /**
          * Определение полей формы создания/редактирования 
публикации.
          *
          * @return list<MoonShineComponent|Field>
          */
         public function fields(): array
         {
             return [
                 Block::make([
                     ID::make()->sortable(),
     
                     Text::make('Заголовок', 'title')->required(),
     
                     // Поле загрузки изображения с сохранением на диск 'public'
                     Image::make('Картинка (файл)', 'image')
                         ->disk('public')
                         ->dir('posts')
                         ->changeFill(
                             fn ($data) => blank($data->image) || 
str_starts_with((string) $data->image, 'http')
                                 ? null
                                 : (string) $data->image
                         )
                         ->nullable(),
     
                     Textarea::make('Текст', 'text')->required(),
                 ]),
             ];
         }
     
         /**
          * Правила валидации для создания и редактирования публикации.
          *
          * @param Post $item
          * @return array<string, string[]|string>
          */
         public function rules(Model $item): array
         {
             return [
                 'title' => ['required', 'string', 'max:255'],
                 'text'  => ['required', 'string', 'max:5000'],
             ];
         }
     }
